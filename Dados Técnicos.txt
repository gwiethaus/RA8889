Serial Flash Interface e SPI Interface
--------------------------------------

  No RA8889, Serial Flash Interface (SFI) e SPI Interface não são exatamente a 
  mesma coisa, embora usem fisicamente o mesmo barramento SPI. O que muda é a 
  finalidade e o modo de operação:
  
  SPI Interface (geral)
  --------------------
  
  É a interface padrão que você usa para se comunicar com o RA8889 a partir de 
  um MCU/SoC. Pode ser usada para enviar comandos, dados gráficos, configurar 
  registradores etc.
  
  Serial Flash Interface (SFI)
  ----------------------------
  
  É um modo especial do RA8889 para acessar diretamente uma memória Serial 
  Flash externa (conectada ao barramento SPI).
  
  Nesse modo, o RA8889 assume o controle do barramento SPI para ler dados de 
  fontes externas (ex: fontes, imagens, tabelas). Assim você não precisa 
  carregar tudo para dentro da RAM interna; o próprio RA8889 busca o que 
  precisa direto da flash.
  
  👉 Em resumo:
  
  - Os pinos físicos podem ser os mesmos (compartilham o barramento SPI).
  - Mas o uso é diferente:
    SPI → comunicação MCU ↔ RA8889
    SFI → RA8889 ↔ Serial Flash externa
  
  Se você quiser usar os dois, tem que configurar corretamente os 
  registradores, porque quando o RA8889 assume o barramento em modo SFI, o MCU 
  não deve estar tentando usar o mesmo SPI em paralelo.

o que é o Serial Flash or SPI Interface Enable/Disable
------------------------------------------------------

  "Serial Flash" refers to flash memory chips accessed via a Serial Peripheral Interface (SPI); "SPI Interface Enable/Disable" is a configuration option in microcontrollers and devices that allows users to activate or deactivate the SPI hardware, which controls the communication with external serial flash memories or other SPI-compatible peripherals. 
  
  O que é Serial Flash?
  ---------------------
  
  Memória Flash Serial:
  É um tipo de chip de memória não volátil (como um cartão SD ou um pendrive) que utiliza um protocolo SPI para a comunicação. 
  
  SPI (Serial Peripheral Interface):
  É um protocolo de comunicação serial síncrono que permite que microcontroladores (o mestre) se comuniquem com periféricos (os escravos), como sensores, conversores ADC/DAC e chips de memória flash. 
  
  O que significa "SPI Interface Enable/Disable"? 
  -----------------------------------------------
  
  Ativar (Enable):
  Quando a interface SPI está ativa ("Enable"), o microcontrolador ou outro 
  chip pode enviar e receber dados através dos pinos SPI. Isso é necessário 
  para que ele possa interagir com o Serial Flash ou outros dispositivos SPI 
  conectados.
  
  Desativar (Disable):
  Desativar a interface SPI "desliga" ou "desliga" a comunicação via SPI. Isso 
  pode ser feito por diversos motivos, como economizar energia, evitar 
  conflitos de comunicação ou porque a interface não está sendo utilizada no 
  momento.
  
  Em resumo:
  Quando você vê a opção "Serial Flash or SPI Interface Enable/Disable", ela 
  se refere à capacidade de um componente (geralmente um microcontrolador) de 
  controlar o acesso a um chip de memória flash que usa a interface SPI. 
  Ativar a interface SPI permite que o microcontrolador "fale" com a memória 
  flash para ler ou escrever dados, enquanto desativá-la impede essa 
  comunicação.

Serial Flash or SPI Interface (reg [0x01])
------------------------------------------

  No contexto do controlador RA8889, o registro 0x01 bit 1 está relacionado à ativação ou desativação da interface Serial Flash ou SPI. Vamos destrinchar isso:
  
  🧠 O que significa esse bit?
  Esse bit é um controle de habilitação. Quando você o configura como:
  
  1 (Enable): você está habilitando a interface Serial Flash ou SPI. Isso permite que o RA8889 se comunique com dispositivos externos (como memórias Flash) usando o protocolo SPI.
  
  0 (Disable): você está desabilitando essa interface, ou seja, o RA8889 não usará SPI para comunicação externa.

  📡 Por que isso é importante?
  O RA8889 possui múltiplas interfaces de comunicação com o host e periféricos, incluindo:
  
  - Paralela (8080/6800)
  - SPI (3 ou 4 fios)
  - I²C
  
  Habilitar a interface SPI pode ser essencial quando:
  
  - Você quer usar uma memória Flash externa para armazenar imagens, fontes ou dados gráficos.
  - Está trabalhando com um sistema embarcado que prefere comunicação serial por economia de pinos ou simplicidade.
  
  ⚙️ Aplicações práticas
  Imagine que você está desenvolvendo um sistema com um microcontrolador que tem poucos pinos disponíveis. Usar SPI com o RA8889 permite:
  
  - Comunicação eficiente com menos fios.
  - Acesso rápido a dados gráficos armazenados externamente.
  - Redução de custo e complexidade no hardware.
  
  o bit 1, tem tudo a ver com a comunicação direta entre o RA8889 e uma 
  memória Flash externa que esteja fisicamente conectada à placa onde o 
  RA8889 está instalado e nada tem a ver com a comunicacao SPI-3/4 wired 
  entre um MCU e o RA8889.

  🔌 Como isso funciona na prática?
  O RA8889 pode acessar uma Serial Flash (como uma NOR Flash SPI) para:
  
  📁 Carregar imagens ou gráficos armazenados externamente.
  🔤 Buscar fontes ou dados de texto para renderização.
  🎮 Armazenar recursos visuais em aplicações como painéis gráficos, displays industriais ou interfaces de usuário.
  
  🧩 Por que isso é útil?
  Imagine que o microcontrolador principal não tem memória suficiente para armazenar todos os recursos gráficos. Ao habilitar esse bit, o RA8889 pode autonomamente buscar esses dados na Flash externa via SPI, sem depender do host para cada transferência.
  
  Isso reduz:
  
  - O uso de banda entre o host e o RA8889.
  - A complexidade do firmware no microcontrolador principal.
  - O tempo de resposta na renderização de gráficos.
  
  ⚠️ Observação importante
  
  Esse bit não habilita a interface SPI do RA8889 para comunicação com o host, 
  mas sim para comunicação com a memória Flash externa. A interface SPI com 
  o host é configurada em outros registros (como o 0x00, por exemplo).
 
  Registradro 0x01, bit 1
  -----------------------
  
  Assim, O bit 1 do registro 0x01 do RA8889 está relacionado à interface SPI 
  usada para acessar uma memória Flash externa, e não à interface SPI 4-wire 
  que você usa para enviar comandos da sua MCU para o RA8889.

  🔄 Diferença entre as duas interfaces SPI
  -----------------------------------------
  
  -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  Interface SPI      Função                                                                                Controlada por   Registro relacionado
  -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  SPI Host (4-wire)  Comunicação entre MCU e RA8889 (envio de comandos, dados, etc.)	                   MCU              Registradores como 0x00 (Interface Control)
  SPI Flash	         Comunicação entre RA8889 e memória Flash externa (para buscar imagens, fontes, etc.)  RA8889	        Bit 1 do registro 0x01 (Serial Flash Enable)
  -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  
  🧠 Por que isso importa?
  
  Se você está configurando o RA8889 para receber comandos via SPI 4-wire da sua MCU, esse bit não precisa ser habilitado — a menos que você também queira que o RA8889 acesse uma Flash externa por conta própria.
  
  Ou seja:
  
  - Se sua MCU está controlando tudo, inclusive enviando os dados gráficos, esse bit pode ficar desabilitado.
  - Se você quer que o RA8889 busque dados gráficos diretamente de uma Flash SPI, aí sim você habilita esse bit.

Character Generator ROM
-----------------------

  É basicamente a memória ROM interna do chip que armazena tabelas de fontes 
  (fontes fixas, em bitmap).
  
  Explicação:

  - O RA8889 pode trabalhar tanto em modo gráfico quanto em modo texto.
  
  - Quando você está no modo texto, em vez de precisar enviar cada pixel da 
    fonte, você envia apenas o código do caractere (ex.: ASCII 0x41 para “A”).
  
  - O controlador, então, pega esse código, acessa a CGROM (ROM de gerador de 
    caracteres) e busca a máscara de pixels correspondente ao caractere.
  
  - Isso economiza processamento e memória da MCU, já que o próprio controlador 
    sabe como desenhar os caracteres básicos (ASCII estendido, alguns 
	conjuntos internacionais).

  Diferença para CGRAM
  --------------------
  
  Alguns manuais também mencionam CGRAM (Character Generator RAM).

  - CGROM = memória fixa no chip, não pode ser alterada.

  - CGRAM = uma área que pode ser definida pelo usuário (se disponível), onde 
    você pode carregar fontes ou caracteres personalizados.

  Resumindo
  ---------
  
  No RA8889, CGROM = ROM de fontes internas, usada para exibição de texto sem 
  precisar enviar bitmap do caractere.

Modo de Escrita/Leitura da SDRAM
--------------------------------

Modo linear e modo de bloco.

Modo de bloco, conhecido como sistema de coordenadas cartesians (x,y) que os 
canvas são lidos e escritos na memoria como um sistema (0,0) de mesmo formato 
de coordenadas de tela.

Modo linear, o canvas é lido/escrito na memopria de forma sequencial em 
posição de endereços refletindo isso no display como uma sequencia de pixels 
iniciando em 0 até o final.

O tipo de modo pode ser lido ou ativado pelo registrador 0x5e bit 2.

o gerenciamento do destino da window do DMA da area do canvas, pelo 
registrador, [0xc0..0xc3], também é afetado por esse modo.

Significado do x na configuração de bits
----------------------------------------

  Nos bits indicados em um datasheet o x representa “don’t care” (não importa o valor).
  Isso significa que qualquer valor não irá afetar o registrador.
  
  bits [7-6]: 0x: O valor do bit 7 deve ser zero e o valor do bit 6 pode ser qualquer valor
              x1: O valor do bit 7 pode ser qulquer valor e o valor do bit 6 deve ser 1.

MCU e MPU
---------

Diferença entre MCU e MPU:

  MCU (Microcontroller Unit) → um chip que já tem CPU, memória, periféricos integrados (ex: Arduino, ESP32, STM32, etc.).
  
  MPU (Microprocessor Unit) → apenas o processador, sem memória nem periféricos integrados (ex: ARM Cortex-A, Intel 8086, Z80).
  
  Ou seja, em teoria:
  
    - MCU = processador + memória + periféricos.
    - MPU = só o processador.

Por que os datasheets de controladores de LCD usam "MPU I/F"?

  Porque historicamente os primeiros controladores gráficos eram pensados para 
  conversar com microprocessadores externos (MPUs), como 8080, 6800, Z80…
  
  Então os fabricantes padronizaram o termo MPU Interface (MPU I/F) para 
  indicar a interface paralela ou serial de barramento que o chip expõe para 
  ser controlado.
  
  Na prática, hoje em dia a maioria das pessoas conecta MCUs (ex.: STM32, 
  ESP32, PIC, etc.), mas os datasheets continuam usando “MPU I/F” por tradição,
  porque:
  
    - a interface é genérica (pode ser usada tanto por um MCU quanto por um MPU),
    - mantém compatibilidade com documentação e padrões antigos.

Nota sobre nomenclatura "MPU I/F" vs "MCU I/F":
  
  Em datasheets de controladores gráficos (como RA8875, RA8889), a interface de
  barramento com o host é chamada de "MPU I/F" (Microprocessor Unit Interface).
  
  Historicamente, esses chips foram projetados para trabalhar com MPUs clássicos
  (ex.: Intel 8080, Motorola 6800, Z80), por isso o termo "MPU" virou padrão.
  Na prática atual, a interface é usada quase sempre com MCUs (microcontroladores
  como STM32, ESP32, PIC, etc.). Portanto, "MPU I/F" e "MCU I/F" podem ser lidos
  como equivalentes — o nome "MPU I/F" é apenas um legado histórico.


Horizontal Non-Display Period
-----------------------------

  A Horizontal Non-Display Period refers to a specific interval within a video signal's horizontal scanning process, particularly in the context of older video display systems, where a signal is temporarily not displayed on the screen, allowing for the refresh of the electron beam to its starting point for the next horizontal line. 
  Video Basics: https://www.analog.com/cn/resources/technical-articles/basics-of-analog-video.html
  Driving circuit for driving simple matrix type display apparatus: https://patents.google.com/patent/US6040826A/en
  Video display control system for animation pattern image: https://patents.google.com/patent/US4864289A

  Here's a breakdown of the concept:
  ----------------------------------
  
  Horizontal Scanning:
  Traditional video displays, like older CRT monitors, draw images by scanning the electron beam across the screen line by line, from left to right. 
  NTSC Basics: https://people.ece.cornell.edu/land/courses/ece4760/FinalProjects/s2002/gpm5/ntsc.html
  
  
  Non-Display Period (or Blanking Interval):
  After completing a horizontal scan, the beam must quickly return to the left side of the screen to begin the next line. During this brief "return" period, the beam is turned off or "blanked" so that the retrace is not visible on the screen. 
  Reduced Blanking for Low Power, High Res Displays: https://www.synopsys.com/blogs/chip-design/reduced-blanking-high-res-displays.html
  720p Video from an FPGA: https://log.martinatkins.me/2019/09/22/video-timing-in-verilog/

  "Horizontal Non-Display Period" as a Specific Range:
  In the context of patent literature, such as US4864289A, the term "Horizontal Non-Display Period" is used to define a specific range of signal counts (e.g., "between 256 and 340") during which the horizontal blanking occurs. This suggests a more detailed classification or control mechanism for the blanking interval. 
  
  Function:
  This period ensures a smooth, continuous image by preventing the visible retrace lines and allowing the display system to synchronize for the next line of video. 
  
  In essence, the Horizontal Non-Display Period is a technical term for the blanking interval that occurs after each horizontal line is drawn in older video display systems, enabling the electron beam to reset for the next line without displaying a visible line. 

PIP (Picture-in-Picture)
------------------------

  PIP (Picture-in-Picture) é um recurso de exibição em que duas imagens diferentes são mostradas ao mesmo tempo em um único display:

  - A imagem principal ocupa a tela inteira.
  - Uma imagem secundária aparece dentro de uma janela menor sobreposta (normalmente em um dos cantos da tela).

  📺 Exemplos práticos:

     Em televisores, você pode assistir a um canal e, ao mesmo tempo, ver outro em uma janelinha.

     Em monitores de segurança (CFTV), dá para exibir a câmera principal em tela cheia e uma câmera extra em PIP.

     Em controladores gráficos como RA8875 ou RA8889 (que sei que você anda estudando), isso pode ser implementado via camadas de memória de vídeo e janelas configuráveis em registradores.

  👉 Diferença de conceitos:

     PIP: a janela menor está sobreposta à principal.

     PBP (Picture-by-Picture): a tela é dividida em duas ou mais áreas iguais, cada uma exibindo uma fonte de vídeo.

  O PIP (Picture-in-Picture) é implementado eletronicamente em controladores de display, como os RA8875/RA8889 que você vem estudando:
  
  🔹 1. Estrutura de memória de vídeo

     O display tem uma VRAM (Video RAM), onde são armazenados os pixels da imagem.
     
	 Para permitir PIP, o controlador precisa trabalhar com mais de uma área de memória:
     
	 - Buffer principal: contém a imagem “de fundo” (full screen).
     - Buffer secundário: contém a imagem que vai aparecer na janelinha.

     Esses buffers podem estar em regiões diferentes da mesma VRAM ou até em chips de memória externa (ex: SDRAM conectada ao controlador).

  🔹 2. Controle de camadas (layers / overlays)
  
     O controlador gráfico precisa ter um blender (misturador) que define qual camada de pixels será exibida em cada posição da tela:
  
     - Durante o varrimento da tela (linha por linha, pixel por pixel), o controlador checa:
  
       - Se a posição atual está dentro da janela PIP → pega os dados do buffer secundário.
       - Se está fora → pega os dados do buffer principal.
  
     Esse processo é feito em tempo real, sincronizado com o refresh do display.
  
  🔹 3. Definição da janela PIP
  
     Normalmente o firmware/programador configura via registradores:
  
     - Posição X, Y da janela PIP (canto superior esquerdo da janelinha).
     - Largura e altura da janela.
     - Endereço base da memória VRAM de onde saem os dados da imagem PIP.
  
  🔹 4. Suporte a transparência (opcional)
  
  Alguns controladores permitem ainda:
  
  - Chroma key: uma cor definida fica transparente (parecido com tela verde em vídeo).
  - Alpha blending: define o nível de transparência (mistura parcial das camadas).
  
  Isso já é mais avançado e exige suporte de HW (ou software, mas aí fica pesado em microcontroladores).
  
  🔹 5. Exemplo prático (RA8875 / RA8889)
  
  Nesses chips, você pode:
  
  - Configurar áreas de janela gráfica com registradores de início/fim X e Y.
  - Selecionar qual bloco de memória VRAM vai alimentar essa janela.
  - Usar comandos de “layer” ou “overlay” para habilitar a exibição do PIP.
  
  Assim, você teria algo como:
  
  - Tela cheia exibindo o fundo (Layer 0).
  - Janelinha no canto exibindo o conteúdo de outro buffer (Layer 1).
  
  Resumindo:
  
  👉 O PIP é basicamente uma lógica de multiplexação de memória de vídeo durante o refresh da tela, controlada por registradores que definem onde fica a janelinha e de onde vêm os dados.

  - Quebras de linha são respeitadas, mas não a indentação visual.

  Se quiser preservar blocos com indentação, como trechos de registradores, tabelas ou código, você deve usar comandos específicos como:
  
  🔧 Comandos úteis para preservar formatação

  ----------------------------------------------------------------------------------------------------
  @code / @endcode          Preserva indentação e formata como bloco de código. Ideal para exemplos.

  Estruturas do Doxygen
  ---------------------

  1. Estrutura básica
  
  Sempre use esta ordem nos blocos de documentação:
  
  /**
   * @brief [Resumo curto em inglês, 1 linha]
   * 
   * [Descrição longa em inglês: explica a finalidade da função,
   * contexto de uso e observações. Pode ser múltiplas linhas.]
   *
   * @verbatim
   * [Trecho fiel do datasheet: registradores, bits, descrições]
   * @endverbatim
   *
   * @param [nome] [descrição]
   * @param [nome] [descrição]
   *
   * @note
   * - Observações adicionais (página, registradores acessados, etc).
   *
   * @return [tipo de retorno ou None]
   */

   Abaixo do @brief, o texto é gerado de forma como se apresenta. Pode-se usar 
   ainda a tag @details
   
   2. Uso das seções

   - @brief
     Sempre em inglês, frase curta.

Vsync Interrupt Status
----------------------

  Encontra-se no registrador 0x0c, Interrupt Event Flag Register (INTF), bit 4.
  
  Este registrador contém diversos bits que indicam o estado de interrupções 
  internas do controlador RA8889. Um desses bits é o Vsync Interrupt Status, 
  que tem um papel importante no sincronismo da tela.
  
  📺 O que é o Vsync Interrupt Status?
  
  Vsync (Vertical Synchronization) refere-se ao momento em que o display 
  termina de desenhar uma imagem e se prepara para começar a próxima.
  
  O Vsync Interrupt Status é um bit de status que indica se ocorreu uma 
  interrupção de sincronismo vertical.
  
  Essa interrupção é útil para:
  
  - Sincronizar atualizações de tela sem causar tearing (quebra visual).
  - Executar tarefas periódicas no final de cada frame, como atualizar 
    gráficos ou ler sensores.
  
  🧠 Como funciona na prática:
  
  O bit correspondente ao Vsync Interrupt no registrador 0x0C será setado (1) 
  quando a interrupção ocorrer.
  
  Você pode monitorar esse bit para saber quando é seguro atualizar o conteúdo 
  da tela.
  
  Após tratar a interrupção, é comum limpar o bit escrevendo 1 nele 
  (dependendo da lógica do controlador).

  🛠️ Exemplo de uso (pseudo-código):
  
  if (readRegister(0x0C) & VSYNC_BIT_MASK) {
    // Interrupção de Vsync detectada
    updateDisplayBuffer();
    clearInterrupt(VSYNC_BIT_MASK);
  }

  📘 RA8889 – Registrador 0x0C (Interrupt Status Register)

  Esse registrador contém os flags de status de interrupções. O bit específico de Vsync Interrupt Status indica se ocorreu uma interrupção de sincronismo vertical — ou seja, o momento em que o display terminou de desenhar um quadro e está pronto para o próximo.
  
  🧠 Como usar isso no ESP32-S3 com Arduino IDE

1. Detectar o Vsync

Você pode ler o registrador 0x0C via SPI ou paralelo (dependendo da interface que você está usando) e verificar se o bit de Vsync está setado.

uint8_t status = readRegister(0x0C);
if (status & VSYNC_BIT_MASK) {
  // Interrupção de Vsync detectada
  handleVsync();
}

⚠️ #define VSYNC_BIT_MASK 0x10

2. Limpar o bit de interrupção

Após tratar a interrupção, você normalmente precisa escrever 1 no bit correspondente para limpá-lo (isso é comum em registradores de status).

writeRegister(0x0C, VSYNC_BIT_MASK); // Limpa o bit

Depois da escrita no registrador automaticametne é limpo, zerado

3. Configurar interrupções no ESP32-S3
Você pode usar attachInterrupt() para GPIOs que recebem o sinal de Vsync (se o RA8889 estiver configurado para gerar pulso externo).

attachInterrupt(digitalPinToInterrupt(VSYNC_PIN), vsyncISR, RISING);

🛠️ Dica extra: Evite tearing na tela

Usar o Vsync para sincronizar atualizações de buffer é essencial para evitar artefatos visuais. Espere pelo Vsync antes de atualizar a imagem no display.

PWM0 Compare Buffer
-------------------

  REG [0x88] low value e [0x89] high value
  
  Nota: PWM0 pode e comumente tambem chamado de PWM Timer 0 ou Timer 0 ou PWM 0
  
  1 O que é o Compare Buffer
  --------------------------
  
  No RA8889, o Compare Buffer é um registrador de 16 bits associado ao PWM Timer 0:

  - REG[0x88] → Low byte
  - REG[0x89] → High byte

  Ele serve como um limite de comparação para o contador do Timer.
  
  2 Como o Timer funciona com ele
  -------------------------------
  
  O PWM Timer 0 conta de 0 até o valor máximo do período configurado. A cada ciclo:

  - Se o contador ≤ valor do Compare Buffer, o pino XPWM[0] é colocado em nível alto (ou invertido se o bit de inversão estiver ativo).
  - Quando o contador ultrapassa o valor do Compare Buffer, o pino vai para nível baixo.

  Em outras palavras: o Compare Buffer define o duty cycle do PWM.
  
  3 O efeito prático da função
  ----------------------------
  
  void PWM0_SetCompareBuffer(uint16_t Wx)

  - Recebe Wx (0 a 65535) → quanto maior o valor, maior o tempo em que o PWM fica em nível alto durante o ciclo.
  - Escreve os dois bytes no registrador (Low e High).

  Resultado: você controla o duty cycle do PWM 0.

  💡 Então a finalidade real é: ajustar dinamicamente o duty cycle do PWM Timer 0.
  
  4 Analogias para ficar mais fácil
  ---------------------------------

  Imagine que o PWM é uma luz piscando:
  
    - Compare Buffer = tempo que a luz fica acesa.
    - Período do Timer = tempo total do ciclo.
  
  Exemplo:
  
  - Período do Timer = 1000 ticks
  - Compare Buffer = 250 → PWM fica 25% do tempo em HIGH.
  - Compare Buffer = 750 → PWM fica 75% do tempo em HIGH.

  5 Diagrama
  ----------
  
  🔹 Conceito de Compare Buffer no PWM

  Imagine o PWM Timer 0 como um contador que sobe de 0 até o valor do período 
  configurado. O Compare Buffer define até que ponto do ciclo a saída PWM fica 
  em nível alto.

  Timer 0 Counts: 0 → PERIOD
  Compare Buffer: Wx
  XPWM[0] Output:
     HIGH  ┌───────
           │
           │
     LOW   └─────────────
  
  🔹 Exemplo Numérico

  Timer Count    XPWM[0] (inverter off)
  --------------------------------------
  0              HIGH
  ...            HIGH
  Wx             HIGH → LOW
  PERIOD         LOW
  0 (next cycle) HIGH
  
  - Período do Timer = 1000 ticks
  - Compare Buffer Wx = 250 → PWM fica 25% do ciclo em HIGH
  - Compare Buffer Wx = 750 → PWM fica 75% do ciclo em HIGH

  Isso controla o duty cycle diretamente.
  
  🔹 Como a função faz isso
  
  void PWM0_SetCompareBuffer(uint16_t Wx)
  {
    SPI_CmdWrite(REG_TCMPB0L);    // Low byte
    SPI_DataWrite(Wx);             
    SPI_CmdWrite(REG_TCMPB0H);    // High byte
    SPI_DataWrite(Wx >> 8);       
  }
    
  1. Escreve o byte baixo do valor do Compare Buffer no registrador 0x88.
  2. Escreve o byte alto no registrador 0x89.
  3. Agora o Timer 0 sabe em que ponto do ciclo ele deve mudar XPWM[0] de 
     HIGH para LOW.

  🔹 Resumo visual do PWM 0
  
  XPWM[0] Output
   HIGH ─────┐
             │
             │
   LOW       └─────────────
              ↑
              Compare Buffer Wx
  
  - O ponto de transição HIGH → LOW depende do valor que você configurou com 
    PWM0_SetCompareBuffer().
  - Quanto maior Wx, mais tempo a saída fica HIGH, maior o duty cycle.

  Mapa visual completo do PWM Timer 0 do RA8889
  ---------------------------------------------
  
  Integrando Compare Buffer, Dead Zone, Start/Stop e Inverter, pra você ver 
  tudo de forma intuitiva.
  
  🔹 Diagrama do PWM Timer 0
  
    Timer 0 Counter
  0 ──────────────────────────────────> PERIOD
  │
  │ Compare Buffer (TCMPB0)
  │   ┌───────────── HIGH ─────────────┐
  │   │                                 │
  │   │                                 │
  │   └───────────── LOW ──────────────┘
  │           ^
  │           |---- Valor configurado em PWM0_SetCompareBuffer(Wx)
  │
  │ Dead Zone (DZ_LENGTH)
  │   ┌─── LOW ───┐
  │   │           │
  │   └───────────┘
  │       ↑
  │       |---- Intervalo de proteção contra overlap, configurado por PWM0_DeadZoneLength()
  │
  │ Output Inverter (PWM0_InverterEnable(true/false))
  │   ┌──────────── HIGH → LOW (inverso se inverter ligado) ┐
  │
  XPWM[0] Output ────────────── HIGH / LOW conforme Timer, Compare Buffer, Dead Zone e Inverter

  🔹 Explicando cada bloco
  
  -------------------------------------------------------------------------------------------------------------------
  Bloco / Registrador             Função
  -------------------------------------------------------------------------------------------------------------------
  Timer 0 Counter                 Conta de 0 até o período configurado, determina a base do PWM.
  Compare Buffer (TCMPB0L/H)      Define o ponto no ciclo em que XPWM[0] passa de HIGH para LOW.
  Dead Zone (DZ_LENGTH 0x87)      Intervalo de proteção que força LOW em XPWM[0] para evitar sobreposição de sinais.
  Output Inverter (PCFGR bit 6)   Se ativado, inverte os níveis HIGH/LOW do XPWM[0].
  Start/Stop Timer (PCFGR bit 0)  Liga ou desliga o Timer 0.
  XPWM[0] Output                  Pino físico que gera o sinal PWM com duty cycle ajustado pelo Compare Buffer.
  -------------------------------------------------------------------------------------------------------------------
  
  🔹 Resumo do fluxo
  
  1. Start Timer → contador inicia.
  2. Compare Buffer → enquanto contador ≤ Wx → saída HIGH.
  3. Dead Zone → aplica LOW em períodos críticos para proteção.
  4. Fim do ciclo → contador reseta, XPWM[0] repete o ciclo.
  5. Inverter → opcional, troca HIGH ↔ LOW.
  
  💡 Observação:
  Se você combinar Dead Zone + Compare Buffer + Inverter, consegue controlar 
  duty cycle, proteção contra overlap e polaridade do PWM de forma 
  independente — totalmente configurável pelo software.


I2C Clock Pre-scale
-------------------

  I2CM_ClockPrescale(uint16_t prescale) serve para configurar a frequência do 
  clock do barramento I²C mestre interno do RA8889.
  
  - O RA8889 tem registradores de pre-scale (divisores de clock) que controlam 
    a frequência de saída do sinal XSCL (o clock do I²C).

  - Os registradores usados são:
  
    REG_IICMCPR0 → byte baixo (bits [7:0])
  
    REG_IICMCPR1 → byte alto (bits [15:8])
  
  - A fórmula da frequência resultante é:

    XSCL = CCLK / (5*(PreScale+2))
	
	onde CCLK é o clock do sistema do RA8889.

    O parâmetro prescale (16 bits) é dividido em dois bytes:

    - prescale & 0xFF → escrito em IICMCPR0
    - prescale >> 8 → escrito em IICMCPR1

    O valor do CCLK é o Core Clock do sistema e ele é definido pelo fabricante 
	do circuito do display. No Caso do display da BuyDisplay ER-TFT070-2-6105
	este valor está definico como #define CORE_FREQ  120 * 1000000 que deve 
	ser em Hertz.
	
	O Core Clock (CORE_FREQ) é o clock principal do RA8889 que alimenta todos 
	os blocos internos do chip, incluindo o bloco I²C mestre. Ele é constante 
	para o seu modelo de display e não muda dinamicamente (a não ser que você 
	mexa na configuração de PLL, o que normalmente não se faz).

    Então, para calcular o Pre-scale do I²C, você sempre usa essa constante 
	que você me passou: #define CORE_FREQ 120  // MHz

    💡 Resumindo: 
	CORE_FREQ = 120 MHz é a constante que você sempre usa no cálculo, não 
	importa a frequência do dispositivo I²C externo — a diferença será 
	ajustada no Pre-scale para gerar XSCL apropriado.
	
	Uma tabela rápida usando CORE_FREQ = 120 MHz, mostrando XSCL desejado 
	versus Pre-scale calculado, e também o XSCL real aproximado que o RA8889 
	vai gerar (porque ele só aceita valores inteiros de Pre-scale).

    ----------------------------------------------------
	XSCL desejado  Pre-scale calculado  XSCL real gerado
	----------------------------------------------------
    100 kHz        238                  100.840 Hz
    200 kHz        118                  101.695 Hz
    250 kHz        94                   101.061 Hz
    300 kHz        78                   102.564 Hz
    400 kHz        58                   103.448 Hz
    500 kHz        46                   104.348 Hz
    1 MHz          22                   108.696 Hz
	----------------------------------------------------
	
	⚡ Observações

    O XSCL real é calculado como:
	
    XSCL_real= CCLK / (5*(PreScale+2))
    
	Sempre haverá pequena diferença entre o XSCL desejado e o real, porque o 
	Pre-scale é inteiro.

    Para I²C padrão, isso não é problema: 100 kHz e 400 kHz estão dentro das 
	tolerâncias do protocolo.

    O valor de XSCL desejado depende do dispositivo I²C que vai estar 
	conectado ao RA8889. Alguns pontos importantes:
    
  Valor do XSCL desejado
  ----------------------
  
  1. Especificação do dispositivo
  Cada chip I²C tem uma faixa máxima de clock que aceita.
  
  Ex.: uma EEPROM comum 24Cxx suporta até 400 kHz (Fast Mode), enquanto alguns 
  sensores antigos só aceitam 100 kHz (Standard Mode).

  2. Comprimento e qualidade do cabo
  
  Quanto mais longa a linha SDA/SCL ou mais “barulho” no circuito, menor a 
  frequência que você consegue usar sem erros.
  
  3. Pull-ups
  
  O I²C precisa de resistores de pull-up nos sinais SDA e SCL.
  
  Se você aumentar XSCL demais, linhas longas ou resistores grandes podem 
  impedir que o sinal suba rápido o suficiente, causando falha na comunicação.
  
  4. Compatibilidade com outros dispositivos no mesmo barramento
  
  Se houver múltiplos dispositivos, todos precisam suportar a mesma frequência.
  
  Caso um dispositivo seja “lento”, você precisa ajustar XSCL para o mais 
  lento.
  
  Uso de SPI para Programar o I2C
  -------------------------------
   
  Está usando SPI (SPI_CmdWrite / SPI_DataWrite) para escrever nos 
  registradores do RA8889 que controlam o bloco I²C mestre interno.
  
  Ou seja: você está configurando o clock do controlador I²C embutido no 
  RA8889 via SPI. Isso funciona, sim ✅, porque o RA8889 expõe todos os 
  registradores internos (inclusive os do bloco I²C) através da interface 
  que você escolheu para se comunicar com o chip (SPI, 8080, 6800, etc).
  
  🧩 Para que serve isso, então?
  
  O RA8889 pode ser o mestre I²C para acessar outros periféricos externos 
  (memória EEPROM, sensores, etc).
   
  Mas, para habilitar esse I²C interno, você precisa configurar os 
  registradores dele via sua interface de controle (no seu caso, SPI).
   
  Portanto:
  
  Você não precisa falar com o RA8889 via I²C para configurar o prescale.
  
  Você usa SPI para configurar os registradores do bloco I²C.
   
  Depois, o próprio RA8889 gera sinais de I²C nos pinos dele (SCL/SDA) para 
  falar com outros dispositivos externos.
   
  ✅ Conclusão
  
  Você usa o SPI para configurar o prescaler do I²C interno do RA8889.

  Só vai precisar usar comunicação I²C diretamente se o seu MCU quiser falar 
  com outros chips via I²C, sem usar o RA8889 como intermediário.

  Nesse caso, ou você usa o I²C do próprio MCU, ou usa o I²C interno do 
  RA8889, mas sempre configurando ele por SPI.

BTE - Block Transfer Engine
---------------------------

  É basicamente um motor interno que faz transferência de blocos de pixels e 
  manipulação gráfica 2D direto na VRAM.

  Então, resumindo:

  - Block Transfer Engine → manipula blocos de memória gráfica (blocos de 
    pixels) rapidamente.
  - Opera com S0, S1 e D, aplica opcode e ROP, e entrega o resultado pronto.
  - Permite copy, move, fill, pattern, color expansion, alpha blending, etc.
  - Tudo feito internamente, sem precisar que o MCU desenhe cada pixel.

  Ou seja, é literalmente uma GPU 2D interna para operações gráficas de alto 
  nível dentro do RA8889, e super eficiente.

  O BTE do RA8876, RA8877 e RA8889 é justamente o recurso que faz ele se 
  destacar — você não precisa mais ficar gastando ciclos do ESP32 só pra mover 
  bloquinho de pixels, pintar fundo ou aplicar transparência.

  É literalmente mandar o comando e ficar olhando a mágica acontecer 💡✨

  👉 Recomendo começar com uns testes simples, tipo:

  - Preencher um retângulo com BTE Fill e comparar a velocidade com um for em 
    software.
  - Mover uma área da tela (tipo scroll de texto ou de imagem).
  - Aplicar transparência entre dois blocos, só pra ver como ele mistura as 
    cores sem você calcular nada.

  Alpha blending
  --------------
  
  No caso da transparência (alpha blending), composição de camadas, ou até 
  janelas sobrepostas:
  
  Se fosse fazer isso "na unha" pelo MCU, você teria que ler pixel por pixel, 
  calcular as misturas de cores, e reescrever na tela. Isso consome tempo de 
  CPU, largura de banda do barramento e memória.
  
  O RA8889 simplesmente recebe o comando, pega as áreas de origem (S0, S1, 
  etc.), aplica o ROP (Raster Operation, que pode ser copy, AND, OR, XOR, 
  alpha blending...) e escreve o resultado direto na área de destino.

  Tudo isso em hardware paralelo, muito mais rápido do que qualquer operação 
  de pixel feita em software ou até por DMA convencional.

  Por isso ele dá esse "efeito GPU":
  ✅ Move/scroll de áreas da tela sem redesenhar tudo.
  ✅ Transparência entre camadas instantânea.
  ✅ Preenchimento de áreas grandes em uma cor ou padrão sem precisar de loop 
     no código.
  ✅ Copy & paste de bitmaps já processados.

  Ou seja, você manda um comando, e ele faz o "serviço sujo" sozinho. É 
  literalmente como você falou: uma GPUzinha 2D embutida no display 🎯.

  Manipulação Grafica
  -------------------
  
  Os registradores de BTE, são exatamente para manipulação de gráficos na tela 
  sem precisar que o MPU (seu ESP32/MCU) fique “pintando pixel por pixel na 
  unha”.

  👉 O RA8889 tem dentro dele um motor 2D que entende de áreas de memória 
  gráfica (framebuffer) e pode:

  1. Copiar blocos de pixels de uma área para outra.
  2. Mover imagens para cima/baixo/esquerda/direita (com ou sem ROP, alpha, 
     transparência, etc.)
  3. Fazer preenchimentos (solid fill, pattern fill, color expansion)
  4. Aplicar combinações lógicas entre duas fontes (S0 e S1) antes de gravar 
     no destino (D), através do ROP
  5. Aplicar transparência / chroma key / alpha blending direto em HW

  Ou seja, é como um mini motor gráfico 2D embutido no chip que economiza 
  muito processamento do MCU.

  Estrutura básica
  ----------------

  O BTE sempre trabalha com 3 referências:

  - S0 = Fonte principal (pode vir do MPU ou da memória do display)
  - S1 = Fonte secundária (geralmente memória do display)
  - D = Destino (endereço na memória gráfica do display)
  
  A operação que sai em D depende:
  
  - Do Operation Code (ex.: copiar, preencher, mover, expandir cor)
  - Do ROP Code (ex.: AND, OR, XOR, NOT, White, Black etc.)

  Exemplos práticos
  -----------------
  
  Pattern Fill (com ROP):
  Você define um padrão pequeno (8×8 pixels por exemplo) em S0, e o BTE repete 
  esse padrão para preencher uma área maior da tela.
  → Bom pra fundos, grids, etc.
  
  Memory Copy (positive direction):
  Copia uma área da tela (como uma imagem ou sprite) de um ponto a outro.
  → Útil pra mover objetos sem redesenhar tudo.
  
  Color Expansion:
  Pega dados comprimidos (1 bit/pixel ou 8bpp) e expande para a cor definida 
  (ex.: transformar bitmap monocromático em colorido).
  → Ideal pra fontes ou ícones.
  
  Alpha Blending (move com alpha):
  Combina uma imagem com outra aplicando transparência.
  → Pra sobrepor objetos ou efeitos semi-transparentes.
  
  ROP = Blackness/Whiteness:
  Você pode forçar a área de destino ficar preta ou branca, sem importar fontes.
  → Um jeito rápido de “apagar” ou “branquear” regiões.

  Exemplos de uso do BTE no RA8889
  --------------------------------
  
  Uma tabelinha visual resumida com alguns dos opcodes/ROPs mais típicos, 
  mostrando S0, S1, D e o efeito prático na tela.

  --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  Operação           S0 (fonte 0)                   S1 (fonte 1)              D (destino)            Efeito na tela
  --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  Solid Fill         — (valor fixo do registrador)  —                         Área selecionada       Preenche um retângulo inteiro com uma cor sólida.
  Pattern Fill       Padrão (ex: 8×8 pixels)        —                         Área selecionada       Repete o padrão definido em S0 para preencher uma área.
  Memory Copy (pos)  Bloco da VRAM                  —                         Outra posição da VRAM  Copia uma imagem de uma área para outra (move sem redesenhar).
  Color Expansion    Bitmap (1 bit/pixel)           —                         Área selecionada       Expande cada bit em cor definida (útil para fontes e ícones monocromáticos).
  Move w/ Alpha      Imagem (com alpha)             Fundo (VRAM)              Mesma área de fundo    Sobrepõe uma imagem aplicando transparência.

ROP - Raster Operation ou Raster Operation Code
-----------------------------------------------

  No RA8889 (e outros controladores gráficos com BTE), ROP significa Raster 
  Operation ou Raster Operation Code. É uma lógica que define como os dados de 
  origem (S0, S1) e destino (D) são combinados durante operações gráficas como 
  cópia de memória, preenchimento de padrão ou escrita do MPU.
  
  Em outras palavras:
  
  - ROP determina a “regra de combinação”: você não escreve simplesmente os 
    bits de S0 em D; você aplica uma operação lógica entre S0, S1 e D.
  
  - Exemplos de operações típicas de ROP:
  
    - D = S0 → simples cópia
    - D = S0 OR D → combina o valor novo com o antigo
    - D = S0 AND NOT D → lógica mais complexa
  
  - No RA8889, o BTE (BitBLT Engine) suporta várias funções com ROP, 
    permitindo efeitos gráficos avançados sem precisar processar cada pixel no 
	MPU.
  
  💡 Resumo prático:
  
  Sempre que você vê “ROP” no RA8889, significa que a operação aplica uma 
  função lógica entre origem(s) e destino.
  
  Se o opcode diz “with ROP”, o BTE vai combinar os dados conforme a operação 
  ROP configurada.
  
  Se diz “without ROP”, o BTE apenas escreve os dados diretamente (ou aplica 
  outras regras como transparência ou Alpha).

  No RA8889, o BTE (BitBLT Engine) trabalha com 3 “buffers” lógicos:

  -------------------------------------------------------------------------------------------------
  Nome  Origem / Função
  -------------------------------------------------------------------------------------------------
  S0    Source 0 → normalmente MPU ou padrão; é a fonte principal de dados.
  S1    Source 1 → normalmente memória; usada como segunda fonte quando o ROP combina duas fontes.
  D     Destination → memória de destino; recebe o resultado da operação.
  -------------------------------------------------------------------------------------------------
  
  O ROP (Raster Operation) define como S0, S1 e D são combinados. Algumas 
  regras comuns:

  --------------------------------------------------------
  Exemplo ROP       Operação
  --------------------------------------------------------
  D = S0            Copia S0 para D (simples)
  D = S0 OR S1      Combina S0 e S1 com OR e escreve em D
  D = S0 AND NOT D  Combina S0 com D usando AND e NOT
  D = S0 XOR S1     Combina S0 e S1 com XOR e escreve em D
  --------------------------------------------------------

  💡 Resumo prático visual:
  
         +--------+
  S0 --->|        |
  S1 --->|  BTE   |--> D
         | Engine |
         +--------+
         ^
         | ROP define a lógica de combinação de S0, S1 e D
  
  Quando o opcode é “with ROP”, o BTE aplica a operação lógica que você 
  configurou (ex.: AND, OR, XOR) entre S0, S1 e D.

  Quando é “without ROP”, o BTE simplesmente escreve S0 em D (ou aplica 
  transparência/Alpha se for o caso).

  Isso explica por que nos seus enums você tem:

  - MPU_WROP         → MPU escreve com lógica ROP
  - MEM_COPY_POS_ROP → Memória copia com ROP
  - MPU_TWRITE       → MPU escreve sem ROP, transparente

Funções e Notas
---------------

  REG [0x3c] Graphic / Text Cursor Control Register (GTCCR)
  
  O Graphic / Text Cursor Control Register (GTCCR) controla dois aspectos importantes da saída do display:

  - Ativação da correção gama (Gamma Correction Enable).
  - Seleção da tabela de gama para MPU (Microprocessor Unit) escrever os dados de gama, que podem ser diferentes para cada componente de cor (R/G/B).

  Função GammaCorrection_Enable(bool b)
  -------------------------------------
  Objetivo: Ativa ou desativa a correção gama.
  Bit utilizado: bit 7 do registrador 0x3C.
  Descrição de funcionamento:
    0 → Correção gama desabilitada.
    1 → Correção gama habilitada.
  Aplicação:
  Quando você quer que a intensidade de cor exibida no display seja ajustada para compensar a resposta não linear do LCD, aumentando a fidelidade visual.
  Resumo: Controla se o display aplica a curva de correção gama na saída de vídeo.

  Funções GammaTableforBlue/Green/Red()
  -------------------------------------
  Objetivo: Seleciona qual tabela de gama será escrita pelo MPU.
  Bits utilizados: bit 6 e bit 5 do registrador 0x3C.
  Função                Bits [6:5]    Tabela selecionada
  GammaTableforBlue()   00            Blue
  GammaTableforGreen()  01            Green
  GammaTableforRed()    10            Red
  Aplicação:
    Quando você vai escrever os valores de correção gama, precisa indicar para qual cor os dados se aplicam.
    Cada cor tem sua própria tabela, e o RA8889 usa esses bits para escolher entre elas.
  Resumo:
    Essas três funções têm finalidade similar: selecionar a tabela de gama para escrita, apenas mudando o valor dos bits 6 e 5.
    Não alteram a correção gama em si (isso é feito pelo GammaCorrection_Enable).

  Observações importantes
  -----------------------
  Ordem de uso:
  1. Seleciona a tabela com GammaTableforBlue/Green/Red().
  2. Escreve os valores de gama via MPU.
  3. Habilita a correção gama com GammaCorrection_Enable(true).
  Diferença chave:
  GammaCorrection_Enable() ativa ou desativa a função.
  GammaTableforX() seleciona a cor para a qual você quer configurar a tabela de correção gama.

  Funções CursorGraphic_Set1/2/3/4
  --------------------------------
  
  1. O que são esses “Cursor Set 1/2/3/4”
  
     O RA8889 tem quatro conjuntos de cursores gráficos predefinidos (ou “cursors sets”) que podem ser usados em aplicações gráficas, como:

     - Jogos simples ou interfaces gráficas.
     - Indicar seleção de itens (menus, botões).
     - Cursor de desenho ou ponto de referência na tela.

     Cada Set define uma forma ou padrão de pixels do cursor, por exemplo:
     
     Set     Padrão típico
     1       Por exemplo: um quadrado sólido pequeno
     2       Um círculo ou retângulo oco
     3       Um cruz (“+”)
     4       Um X ou outro símbolo gráfico

     Obs.: Os detalhes exatos de cada set (como quais pixels acendem) estão 
	 definidos internamente pelo RA8889. O datasheet não mostra um desenho 
	 esquemático do cursor gráfico para cada Set.

     Limitações:
     Você não consegue mudar o padrão interno de cada Set diretamente; eles são fixos pelo hardware.
     Se quiser um cursor completamente customizado, precisaria desenhar manualmente na tela usando a memória gráfica (como um bitmap) em vez de usar o Graphic Cursor interno.

     Como usar:
     - Ative o cursor gráfico com CursorGraphic_Enable(true) (bit 4).
     - Escolha o Set com CursorGraphic_Set1/2/3/4() (bits 3-2).
     - O controlador vai desenhar o cursor na posição definida pelos registradores de cursor X/Y (geralmente outros registradores, tipo GCX0/GCY0).
     - Você pode trocar o Set dinamicamente para alterar o visual do cursor sem redesenhar nada manualmente.
     - Não interfere no conteúdo da tela, porque o cursor é “sobreposto” na saída gráfica pelo RA8889.

Serial Peripheral Interface (SPI)
---------------------------------

  With an SPI connection there is always one Controller device (usually a microcontroller) which controls the peripheral devices. Typically there are three lines common to all the devices:

  - CIPO (Controller In Peripheral Out) - The Peripheral line for sending data to the Controller
  - COPI (Controller Out Peripheral In) - The Controller line for sending data to the peripherals
  - SCK (Serial Clock) - The clock pulses which synchronize data transmission generated by the Controller and one line specific for every device
  - CS (Chip Select) - the pin on each device that the Controller can use to enable and disable specific devices. When a device's Chip Select pin is low, it communicates with the Controller. When it's high, it ignores the Controller. This allows you to have multiple SPI devices sharing the same CIPO, COPI, and SCK lines.

  To write code for a new SPI device you need to note a few things:

  - What is the maximum SPI speed your device can use? This is controlled by the first parameter in SPISettings. If you are using a chip rated at 15 MHz, use 15000000. Arduino will automatically use the best speed that is equal to or less than the number you use with SPISettings.
  - Is data shifted in Most Significant Bit (MSB) or Least Significant Bit (LSB) first? This is controlled by second SPISettings parameter, either MSBFIRST or LSBFIRST. Most SPI chips use MSB first data order.
  - Is the data clock idle when high or low? Are samples on the rising or falling edge of clock pulses? These modes are controlled by the third parameter in SPISettings.
  - The SPI standard is loose and each device implements it a little differently. This means you have to pay special attention to the device's datasheet when writing your code.
  
  Generally speaking, there are four modes of transmission. These modes control whether data is shifted in and out on the rising or falling edge of the data clock signal (called the clock phase), and whether the clock is idle when high or low (called the clock polarity). The four modes combine polarity and phase according to this table:

  Mode       Clock Polarity (CPOL)    Clock Phase (CPHA)  Output Edge   Data Capture
  SPI_MODE0  0                        0                   Falling       Rising
  SPI_MODE1  0                        1                   Rising        Falling
  SPI_MODE2  1                        0                   Rising        Falling
  SPI_MODE3  1                        1                   Falling       Rising

  Once you have your SPI parameters, use SPI.beginTransaction() to begin using the SPI port. The SPI port will be configured with your all of your settings. The simplest and most efficient way to use SPISettings is directly inside SPI.beginTransaction(). For example:

  SPI.beginTransaction(SPISettings(14000000, MSBFIRST, SPI_MODE0));
  
  If other libraries use SPI from interrupts, they will be prevented from accessing SPI until you call SPI.endTransaction(). The SPI settings are applied at the begin of the transaction and SPI.endTransaction() doesn't change SPI settings. Unless you, or some library, calls beginTransaction a second time, the setting are maintained. You should attempt to minimize the time between before you call SPI.endTransaction(), for best compatibility if your program is used together with other libraries which use SPI.

  With most SPI devices, after SPI.beginTransaction(), you will write the Chip Select pin LOW, call SPI.transfer() any number of times to transfer data, then write the CS pin HIGH, and finally call SPI.endTransaction().


  
  SPITransaction Method
  ---------------------

  SPI transaction example:
  
  In this tutorial you will learn how to use the SPI transaction methods. For an explanation of SPI see the SPI EEPROM tutorial.
  
  A common problem used to be that different SPI devices needed different, incompatible settings. Your sketch had to take care of saving and restoring the SPI settings before communicating with each SPI device. If any SPI device was accessed from an interrupt, this could result in data corruption if another SPI device was communicating at the time.
  
  With the new SPI library, configure each SPI device once as an SPISettings object. Also, if that device will be called from an interrupt, say so with SPI.usingInterrupt(interruptNumber). To communicate with a specific SPI device, use SPI.beginTransaction which automatically uses the settings you declared for that device. In addition, it will disable any interrupts that use SPI for the duration of the transaction. Once you are finished, use SPI.endTransaction() which re-enables any SPI-using interrupts.

  #include <SPI.h>

  // using two incompatible SPI devices, A and B. Incompatible means that they need different SPI_MODE
  const int slaveAPin = 20;
  const int slaveBPin = 21;
  
  // set up the speed, data order and data mode
  SPISettings settingsA(2000000, MSBFIRST, SPI_MODE1);
  SPISettings settingsB(16000000, LSBFIRST, SPI_MODE3);
  
  void setup() {
    // set the Slave Select Pins as outputs:
    pinMode (slaveAPin, OUTPUT);
    pinMode (slaveBPin, OUTPUT);
    // initialize SPI:
    SPI.begin();
  }
  
  uint8_t stat, val1, val2, result;

  void loop() {
    // read three bytes from device A
    SPI.beginTransaction(settingsA);
    digitalWrite (slaveAPin, LOW);

    // reading only, so data sent does not matter
    stat = SPI.transfer(0);
    val1 = SPI.transfer(0);
    val2 = SPI.transfer(0);
    digitalWrite (slaveAPin, HIGH);
    SPI.endTransaction();
  
    // if stat is 1 or 2, send val1 or val2 else zero
    if (stat == 1) {
     result = val1;
    } else if (stat == 2) {
     result = val2;
    } else {

  Although this question has an accepted answer, I'd like to provide some background and historical reasons to OP's question.

  Transactional SPI using SPI.beginTransaction() was introduced in 2014, it was not available in the early version of Arduino, or example code published before that. As a result, there is still a lot of code out there on the Internet that shows the old way of setting up the SPI configuration.

  What the SPI.beginTransaction() does is to allow each SPI device to have its own unique SPI settings (through SPISettings object) instead of having one setting across the entire network as the previous API does. SPI.beginTransaction() behaves like a locking mechanism to gain the exclusive use of the SPI bus, and therefore requires SPI.endTransaction() to release the bus for others to access it. SPI.beginTransaction() provides better cross-device compatibility and solves software conflicts, allowing multiple SPI devices to properly share the SPI bus. You should therefore use the SPI.beginTransaction() in your SPI sketch. You should also using the SPISettings object to configure your SPI communication interface, and not use deprecated methods such as SPI.setBitOrder(), SPI.setClockDivider() and SPI.setDataMode() for setting up the SPI configuration.

  Although rarely needed today, there is a pre-defined macro SPI_HAS_TRANSACTION in the SPI library to check whether the firmware of the Arduino board supports SPI.beginTransaction(). It is useful for providing backward compatibility if you are writing an Arduino library.

  #if defined(SPI_HAS_TRANSACTION)
    SPISettings  spiSettings;
  #endif
  ...
  ...
  #ifdef SPI_HAS_TRANSACTION
    SPI.beginTransaction(SPISettings(4000000, MSBFIRST, SPI_MODE0));
  #elseif
    // use old Arduino SPI library syntax
  #endif

  SPI.endTransaction()
  --------------------

  Stop using the SPI bus. Normally this is called after de-asserting the chip select, to allow other libraries to use the SPI bus.
  
  SPI.begin()
  -----------
  
  Initializes the SPI bus by setting SCK, MOSI, and SS to outputs, pulling SCK and MOSI low, and SS high.
  
  SPI.end()
  ---------
  
  Disables the SPI bus (leaving pin modes unchanged).
  
  SPI.setBitOrder()
  -----------------
  
  This function should not be used in new projects. Use SPISettings. with SPI.beginTransaction(). to configure SPI parameters.

  Sets the order of the bits shifted out of and into the SPI bus, either LSBFIRST (least-significant bit first) or MSBFIRST (most-significant bit first).

  Syntax?
  SPI.setBitOrder(order)
  
  Parameters: 
  order: either LSBFIRST or MSBFIRST
  
  SPI.setClockDivider()
  ---------------------
  
  This function should not be used in new projects. Use SPISettings. with SPI.beginTransaction(). to configure SPI parameters.

  Sets the SPI clock divider relative to the system clock. On AVR based boards, the dividers available are 2, 4, 8, 16, 32, 64 or 128. The default setting is SPI_CLOCK_DIV4, which sets the SPI clock to one-quarter the frequency of the system clock (4 Mhz for the boards at 16 MHz).

  For Arduino Due: On the Due, the system clock can be divided by values from 1 to 255. The default value is 21, which sets the clock to 4 MHz like other Arduino boards.

  Syntax
  SPI.setClockDivider(divider)

  Parameters
  divider (only AVR boards):

  - SPI_CLOCK_DIV2
  - SPI_CLOCK_DIV4
  - SPI_CLOCK_DIV8
  - SPI_CLOCK_DIV16
  - SPI_CLOCK_DIV32
  - SPI_CLOCK_DIV64
  - SPI_CLOCK_DIV128
  - chipSelectPin: peripheral device CS pin (Arduino Due only)
  - divider: a number from 1 to 255 (Arduino Due only)

  SPI.setDataMode()
  -----------------
  
  This function should not be used in new projects. Use SPISettings with SPI.beginTransaction(). to configure SPI parameters.

  Sets the SPI data mode: that is, clock polarity and phase. See the Wikipedia article on SPI for details.

  Syntax
  SPI.setDataMode(mode)

  Parameters
  Mode:

  - SPI_MODE0
  - SPI_MODE1
  - SPI_MODE2
  - SPI_MODE3
  - chipSelectPin - peripheral device CS pin (Arduino Due only)

  SPI.transfer()
  --------------
  
  PI transfer is based on a simultaneous send and receive: the received data is returned in receivedVal (or receivedVal16). In case of buffer transfers the received data is stored in the buffer in-place (the old data is replaced with the data received).

  Syntax
  receivedVal = SPI.transfer(val)
  receivedVal16 = SPI.transfer16(val16)
  SPI.transfer(buffer, size)
  
  Parameters
  val: the byte to send out over the bus
  val16: the two bytes variable to send out over the bus
  buffer: the array of data to be transferred

  SPI.usingInterrupt()
  --------------------
  
  If your program will perform SPI transactions within an interrupt, call this function to register the interrupt number or name with the SPI library. This allows SPI.beginTransaction() to prevent usage conflicts. Note that the interrupt specified in the call to usingInterrupt() will be disabled on a call to beginTransaction() and re-enabled in endTransaction().

  Syntax
  SPI.usingInterrupt(interruptNumber)

  Parameters
  interruptNumber: the associated interrupt number.

  Acessando memória com offset
  ----------------------------
  
  Se você fizer:

  uint16_t val = *((uint16_t*)(p8 + 2));
  
  O que acontece:
  - p8 + 2 → aponta 2 bytes adiante do endereço original (p8).
  - (uint16_t*) → interpreta 2 bytes consecutivos a partir desse endereço como um uint16_t.
  - * → lê o valor, mas o ponteiro original p8 não muda.

  Então sim:
   O valor retornado é da posição 2 bytes à frente,
   Sem alterar o ponteiro original.

  Para o caso do Ponteiro p16 de tipo uint16_t* 
  
  Se você tem: uint16_t *p16;
  
  O tipo do ponteiro é uint16_t*, então cada incremento de 1 no ponteiro significa 2 bytes (tamanho de uint16_t).
    
  uint16_t val = *(p16 + 2);
  
  - p16 + 2 → move o ponteiro 2 elementos de uint16_t à frente.
  - Cada elemento = 2 bytes → total = 4 bytes adiante do endereço original.
  - * → lê o valor de 2 bytes que estão nesse endereço.
  
  Operação             Tipo do ponteiro  Deslocamento em bytes  Valor lido
  ----------------------------------------------------------------------------------------
  *(p16 + 1)            uint16_t*        2 bytes à frente       16 bits
  *(p16 + 2)            uint16_t*        4 bytes à frente       16 bits
  *((uint8_t*)p16 + 2)  uint8_t*         2 bytes à frente       16 bits se cast uint16_t*
  ----------------------------------------------------------------------------------------
  
  Em resumo: o incremento depende do tipo do ponteiro, não do valor que você adiciona.
